# Post-Apollo Notifications // Proton Mail dual-adapter contract

**State:** Development foundation. **No mailbox integration is live.**

This file documents only the Notifications implementation boundary; it is not a Hospital authority rule. Do not enable account access, mailbox mutation or browser extension installation merely by merging this code.

## Goal

One Notifications **MAIL** deck, two independently authenticated adapters:

- **Browser companion (Chromium + Firefox):** Free and paid Proton plans. Must inspect only an explicitly authorized Proton Mail tab. Proton native Snooze is possible only after the site interaction, message selection and result can be reliably verified. No private undocumented Proton HTTP API assumed.
- **Proton Mail Bridge:** Paid plan, IMAP loopback. Read, Archive, Trash, Spam and Star may be implemented with verified IMAP mailbox identity/flags. Native Snooze is NOT supplied by Bridge, even on paid plans.

The MAIL deck already exists. Native notification actions remain available when the sender advertises them, but these are unrelated to provider authentication. Until a real adapter provides a verified message reference, the six buttons **stay disabled**.

## Architecture

```text
Browser notification --> NotificationsService (history + notification id)
                               |
                  PRIVATE trusted message binding
                               |
                      Mail action policy
                               |
            +------------------+------------------+
            |                                     |
    Browser Companion                    Bridge IMAP (paid)
    Proton origin only                   loopback + verified TLS
    Snooze + supported web ops           five IMAP-supported ops
            |                                     |
            +------------------+------------------+
                               |
                 Provider-confirmed result receipt
                               |
                  MAIL UI final state update
```

## Invariants

1. **One message, one action, one adapter.** The planner prefers Bridge for its five supported actions and the browser for Snooze. It can choose the browser for another action only if that adapter independently has a verified identity for the exact message and advertises that capability. No silent retry on a second adapter after a partial/uncertain mutation.
2. **Never guess identity from subject, sender, notification text, timestamps, web hostname, HTML position, or an apparent Proton internal URL.** A binding must be generated by an authenticated, trusted adapter from a verified message. Browser and Bridge message references are not assumed equivalent.
3. A binding is private and expires; **do not persist opaque references or secrets in notification history**. No Proton account password, Bridge-generated password, cookies, browser storage tokens, message body or unencrypted mail content should be logged or put on the desktop notification bus.
4. **Trash and Spam require explicit confirmation.** Clicking an available MAIL action is not an authorization to touch another email.
5. Provider dispatch means **pending**, not success. Show completion only after a verified response matching the same action, account, event, message reference and request id; reconnect/failure/timeout must not infer success.
6. Bridge must bind **127.0.0.1**, a verified TLS mode/certificate, a single authenticated account, and **UIDVALIDITY + UID + mailbox**. An IMAP move can change UID, so the adapter must refresh binding/receipt before subsequent actions. Never bypass certificate verification or use a Proton account password instead of Bridge credentials.
7. The browser companion must pin the exact extension identity in the native-host allowlist: Chromium uses `allowed_origins` plus a `chrome-extension://` caller; Firefox uses `allowed_extensions` plus the explicit Gecko add-on ID. The native host independently checks the caller using browser-specific launch arguments. The native host manifest and extension installation are **separate explicit operator approvals**. No extension broad browsing permissions, page-injected scripts or session-token copying.
8. Preserve Notifications SITE/APP, DND, ZZ, FAVS, CLEAR ALL, native default click, Apollo widget routes and ⇲ Bring Here. **Mail Snooze is not Notification ZZ; Mail Star is not Notification Favorites.**

## Implemented in this slice

- `services/notifications/mail/ProtonMailActionPolicy.js`: pure deny-by-default action selection, account binding, destructive action confirmation gate, provider receipt verification.
- `ProtonBrowserCompanionPolicy.js`: exact Proton origin and capability attestation policy; no verified mailbox reference means no capabilities.
- `ProtonBridgeAdapterPolicy.js`: loopback/certificate prerequisites; five supported operation names, no Snooze and no socket writes.

It sends **no message identities, mail contents, credentials or mutation operations**. The host refuses all commands except a versioned PING and always reports `mailboxAccess:false`.

## Private notification-to-message binding ledger foundation (2026-10-22)

`services/notifications/mail/ProtonMailBindingLedger.js` now contains an
**offline-only, memory-only** binding ledger for a *future* authenticated
Proton adapter. It is intentionally **not imported or instantiated by
NotificationsService** and not reachable from the MAIL controls or browser
companion. The current native host still permits only `PING`; the V4 browser
probe only reports counts and `identity NOT verified`.

The ledger constructor requires **two independently owned trusted callbacks**:

1. `verifyFromTrustedAdapter(proposal)` must authenticate the adapter source,
   account, exact message and its association with the intended live native
   notification, and return a *new, verified internal record*. It must never
   merely echo a browser page observation, an arbitrary `attested:true` field,
   a selected-row ID, notification title/subject, timestamp or guessed URL.
2. `isLiveEvent(eventId)` must check the real transient
   `NotificationsService.liveExternalNotifications` registry, not retained
   notification history. There is currently **no approved transport or
   production implementation** of either callback.

Without both trusted callbacks, admission returns
`transport-not-connected`. The ledger validates short-lived binding shape
and account/reference consistency, caps a lease at **two minutes**, limits
active leases to **64**, prevents a browser or Bridge reference from being
bound to two simultaneous native events, revokes on notification expiry or
closure, and temporarily tombstones revoked leases to reject stale replay.
Lookups return private defensive copies. A disconnected/changed transport
must call `reset()` to revoke current leases and must disable new admission.

The only authorized use of `lookup()` will be inside a reviewed trusted
notification/adapter controller, followed by the existing
`ProtonMailActionPolicy.routeFor()`. Never serialize its result into a
ListModel, notification history, log, shell/DBus notification payload or
browser-extension console. The `attested` booleans in the **returned** record
are not cryptographic proofs. The authenticating transport and exact
event-to-message correlation remain separate prerequisites.

Offline tests in `tests/notifications/test_proton_binding_ledger.py`
exercise rejected self-asserted claims (including V4 browser results),
account/ref mismatch, expiry, duplicate event and message, closed event,
revoke/reset/replay, capacity, defensive copies and policy compatibility.
They use synthetic trusted callbacks only, do not authenticate Proton, do
not enable any MAIL action, and create no private mail content.

### Next gated implementation

- Decide and review how the approved browser/Bridge adapter proves a
  **specific notification delivery** corresponds to an **individual email**
  rather than a conversation, from an authenticated per-account source.
- Implement exact browser-native host identity pinning, a private local
  transport protocol, and message-proof validation with no credentials or
  opaque references in notification history.
- Integrate the trusted event liveness callback and ledger inside
  `NotificationsService` only after end-to-end tests. A published
  notification cannot confer its own binding just by claiming an ID.
- Obtain an adapter-side provider-confirmed operation receipt and enforce
  at-most-one dispatch, expiry, revocation and explicit destructive-action
  confirmation. Activate a local writer only with operator permission.

## Native host ↔ Quickshell local probe transport (2026-10-22)

GitHub development stage **only**. The existing browser companion continues to
send its original read-only PING. The browser extension is not modified and
the desktop's live NotificationsService is not modified by this stage.

**Server (dormant)**: \`services/notifications/mail/ProtonRelayPilot.qml\`
uses the Quickshell 0.2.1 \`Quickshell.Io.SocketServer\` / \`Socket\` /
\`SplitParser\` Unix-socket API. It is neither instantiated nor imported and
has literal \`active: false\`, including when independently loaded. It accepts
only a constant \`{"protocol":1,"kind":"PROTON_RELAY_PROBE"}\` request and
replies with \`PROTON_RELAY_ACK\`, \`mailboxAccess:false\`,
\`messageIdentityVerified:false\` and zero capabilities. It exposes no
notification counts, references, message IDs, mail subjects or credentials.

**Client (native host)**: \`integrations/proton/browser/proton_native_host.py\`
preserves its exact caller-pinned browser PING/PONG. Its *additional*
\`{"protocol":1,"kind":"RELAY_PING"}\` request can only attempt the local
socket when the native-host **process** has
\`POST_APOLLO_PROTON_RELAY_ENABLE=1\`. The endpoint is restricted to the
canonical \`$XDG_RUNTIME_DIR/post-apollo-proton-relay.sock\`, never a caller-
supplied path. The runtime directory and socket must be owned by the current
user, deny group/other permissions, and not be symlinks. The host uses a
500 ms timeout and Linux Unix-domain \`SO_PEERCRED\` to verify the other
endpoint belongs to the current UID, then sends only the constant probe.
Any missing endpoint, bad response, untrusted browser caller or mismatched
permissions fails closed without activating mailbox capabilities.

A successful optional relay roundtrip returns only \`RELAY_PONG\` with
\`desktopConnected:true\`, \`mailboxAccess:false\`,
\`messageIdentityVerified:false\`, \`capabilities:[]\`.
**This is transport reachability, NOT proof of a Proton account, a mail
message, or its relation to a specific notification.** Same-UID local process
impersonation is not solved by file permissions and \`SO_PEERCRED\`, so future
mail-operation protocols need their own reviewed authorization,
replay protection and event-specific authenticated evidence.

The dormant receiver currently cannot actually accept a connection; this
is intentional. The only executable end-to-end test is the Python fixture
in \`tests/notifications/test_proton_local_relay_pilot.py\`, which creates
a temporary private Unix socket with a simulated peer. CI verifies the
same-UID check, exact byte protocol, bad replies, wrong caller, default off,
endpoint mode and symlink rejection.

**Future explicit operator approvals** are required to register the native
host on the actual machine; activate the Quickshell socket; connect it to
NotificationsService's live event lifecycle; and separately enable verified
message identity, account authentication, action dispatch and receipts.
Merging this patch does none of those things. The six MAIL buttons remain
gated, and the private binding ledger is still not imported into the live
NotificationsService.

## Notification-to-message correlation proof gate (2026-10-23)

**Current issue observed:** The operator has verified a single selected Proton row
(\`selectedMailRows=1\`, \`selectedRowStructureOk=true\`) and a real enabled
\`toolbar:read\` button. That does not connect this row to any Quickshell
notification.

**Upstream source finding:** Proton WebClients' current web-mail
\`applications/mail/src/app/hooks/mailbox/notifications/notificationHelpers.ts\`
calls \`create(title, { tag: notificationData.ID, ... })\`, where
\`notificationData.ID\` is the actual \`message.ID\`. In conversation mode its
click-through location may instead use a conversation \`elementID\` plus a
separate \`messageID\`; grouped notifications do not represent one message.
The helper in \`packages/shared/lib/helpers/desktopNotification.ts\`
creates a browser \`new Notification(...)\`. However, **the existing
Quickshell notification intake does not expose a verified link to the
web Notification's \`tag\`**: \`NotificationsConverter.qml\` only maps app
metadata and displayed fields, while \`NotificationsService.qml\` generates
its own \`eventId\` upon receiving an OS notification. A notification title,
sender, timestamp, website host, browser click-through URL or hypothetical
string-equal \`tag\` is therefore insufficient and must never be used as an
authentication shortcut.

- https://github.com/ProtonMail/WebClients/blob/main/applications/mail/src/app/hooks/mailbox/notifications/notificationHelpers.ts
- https://github.com/ProtonMail/WebClients/blob/main/packages/shared/lib/helpers/desktopNotification.ts

**New offline policy:** \`services/notifications/mail/ProtonNotificationCorrelationPolicy.js\`
exports \`makeVerifier(nativeDeliveryFor, providerMessageFor, isLiveEvent,
now)\`. This can be supplied to the existing memory-only
\`ProtonMailBindingLedger.createLedger()\` only by a trusted controller.

- \`nativeDeliveryFor(eventId)\` must retrieve an independently authenticated
  record, generated *at the notification-delivery boundary*, with exact
  provider provenance, stable source-event correlation key, account, **single**
  message identity and delivery time. It must not merely reconstruct a record
  from the OS notification's summary/body/app name.
- \`providerMessageFor(adapterTicket)\` must retrieve an independently
  provider-verified single-message record containing the **same** source event
  key, account and exact message reference. A user-selected row ID or an
  externally asserted \`attested:true\` field is not a verified provider
  witness, and a conversation record is not a single message.
- Only when both independently authenticated records agree, the event is
  still live, and both records are fresh does this pure policy return a
  private ledger-compatible binding. It exports no subject, body, link,
  native event source key or adapter ticket.
- Without either trusted provider, it fails closed and returns no binding.
  Neither callback has a real implementation today. A shared key copied from
  untrusted data is **not** proof: real producers still must establish the
  origin/authority of each record.

**No new permissions, native host messages, Quickshell wiring, mailbox
actions or local install.** Tests simulate separate evidence registries,
correct and mismatched keys/account/message, grouped/conversation events,
expired and revoked events, forged proposals and compatibility with the
existing routing/ledger policy. They are *not* a successful live provider
correlation test.

**Operator choice needed before live pairing:** Determine which *actual
supported* mechanism will provide trustworthy event-level evidence for
Brave/free Proton. A reviewed provider-side notification producer or an
explicit verified, single-message pairing UX are candidates, but neither
is approved or implemented. Do not assume browser Web Notifications expose
their per-message \`tag\` through the desktop notification protocol.
Paid Bridge is another adapter, not an automatic browser-event match.

## Chromium/Brave native notification provenance feasibility (2026-10-23)

### Why this is a blocker

Proton's public WebClients notification helper uses \`message.ID\` as the
\`tag\` of the **web** Notification. The **OS desktop** notification seen by
Quickshell travels through Brave/Chromium's Linux
\`org.freedesktop.Notifications.Notify\` bridge. A public Chromium Linux
implementation sends the title, body, actions, app metadata and limited
hints to D-Bus, but does **not obviously forward the Web Notification's
per-message tag or internal browser notification ID as a usable hint**.
Chromium stores its own notification ID behind the Linux bridge's
\`dbus_id\` correlation. This is evidence of a likely architectural
limitation, NOT yet live proof about the operator's installed Brave build.

Relevant sources:
- Proton's notification creation:
  https://github.com/ProtonMail/WebClients/blob/main/applications/mail/src/app/hooks/mailbox/notifications/notificationHelpers.ts
- Chromium Linux D-Bus adapter:
  https://chromium.googlesource.com/chromium/src/+/512a3a91af1b57f0be8c0e2e5dc88e4b6cac1248/chrome/browser/notifications/notification_platform_bridge_linux.cc
- Freedesktop D-Bus notification protocol:
  https://specifications.freedesktop.org/notification/latest-single/

Do not assign a trusted message identity from a notification title/body,
sender, origin text, timestamp, guessed web tag, or numeric D-Bus ID.
\`ProtonNotificationCorrelationPolicy.js\` remains fail-closed until a
genuine producer establishes exact account/message/event provenance.

### Privacy-bounded experiment (NOT auto-activated)

To distinguish Brave's actual desktop metadata capabilities,
\`services/notifications/mail/ProtonNativeDeliveryAudit.js\` adds an opt-in
helper to \`NotificationsService.qml\`. When the **Quickshell process**
starts with \`POST_APOLLO_PROTON_DELIVERY_AUDIT=1\`, it logs only the presence
of fixed named hints and small counts, at most **12** browser-candidate
deliveries per shell session, separated by at least one second. It never
logs raw hint keys or values, the browser's app name, titles, addresses,
subjects, URLs, message IDs, action labels, cookies or page content.

Illustrative diagnostic format (values shown are examples only):

\`\`\`text
PA_PROTON_DELIVERY_AUDIT hintCount=3 categoryHint=false desktopEntryHint=true kdeOriginHint=true tagHint=false actionCount=2 identity NOT verified
\`\`\`

The fixed-name \`tagHint\` flag only detects explicitly named tag-style
keys. Even \`tagHint=true\` is NOT an authenticated per-message reference,
and \`false\` does NOT prove that no other implementation-specific field
exists. Note that an unrelated browser notification may also produce
a sample; the user should correlate the result with the arrival of a
new Proton mail notification by time alone, without posting its text.

**Default is OFF.** No installation, service restart, environment changes
or local write is part of this GitHub code change. Before testing live,
obtain separate operator permission to update the local working tree and
restart/reload Quickshell with the temporary opt-in environment variable;
preserve the existing running shell and rollback option.

### Architecture decision after live audit

If Brave does not deliver authenticated message-event provenance, **stop
trying to infer it from native notifications**. Preferred practical route:
Post-Apollo-owned opt-in notification producer, where a browser-side adapter
first verifies a single message, then registers a generated event reference
through a reviewed native channel *before* publishing its own desktop
notification. In that design, Post-Apollo controls the event and reference
registry. Requires explicit operator review of browser site permissions,
producer UX, identity proof, duplicated native notifications, account
transitions, and provider-confirmed actions.

Manual per-message pairing is an alternative only with a deliberate user
confirmation and a clear distinction between user-attested selection and
provider-verified message identity. Neither path is approved for activation.

## Click-only browser Notification event observation pilot (2026-10-23)

**Problem addressed:** The operator's live Brave/Quickshell audit reported
`hintCount=4`, `desktopEntryHint=true`, `tagHint=false`,
`actionCount=2`, and **identity NOT verified** for a browser-originated
notification. Proton's public mail client creates a Web Notification with
`tag: notificationData.ID`, but Brave's native desktop notification bridge
does not show the message tag in any of the recognized hint fields. Further
native metadata guessing is not warranted.

**This stage is observation only, NOT a producer or mailbox adapter.** No
host permissions, all-sites registration, content-script manifest entries,
mailbox APIs, provider credentials, desktop notification creation or mailbox
mutations are added.

The shared Chromium/Firefox extension adds an optional **user-click-scoped**
`notification_event_pilot.js` launched by `background.js` into **only
the exact active `https://mail.proton.me` top-level tab**, using the already
granted `activeTab` and `scripting` permissions and `world: "MAIN"`.

1. On the **first** companion toolbar click, the page-realm script temporarily
   wraps the page's `window.Notification` constructor with a pass-through
   `Proxy`, tracking **only the capped number of construction attempts**.
   It never inspects or stores constructor arguments, title, body, tags,
   message IDs, email addresses, URLs, cookies or page storage.
2. The wrapper calls the original constructor with unchanged arguments and
   new-target; static properties remain delegated through the Proxy.
   **This is instrumenting page JavaScript, not passive observation**.
   Proton can detect or interfere with it; site behavior may differ. No
   result is authoritative identity evidence.
3. A **second** companion click within 90 seconds stops counting, restores
   the original constructor if nobody else replaced it, and logs a line
   containing only `stage=stopped attempts=N capped=false/true` plus
   `identity NOT verified` to the **extension service-worker console**.
   After 90 seconds the script automatically restores the constructor;
   the next click reports `stage=expired` and the count. Further clicks
   can begin a fresh window. A page reload or navigation discards the
   in-page state. The cap is 20 attempts.
4. If there is no writable `window.Notification`, an unsupported injection
   context, a property collision or a browser API error, report only
   `unavailable`. No attempt is made to force an injection, bypass CSP,
   change browser permissions or restore over another script's replacement.

The original V4 readiness probe and native `PING` still run on each click;
a missing native host remains expected. The new event data is never sent to
the native host, the OS notification service, the Quickshell history/ledger
or the Post-Apollo MAIL actions.

**Limits that materially affect interpretation:**

- `attempts>0` proves only that the current page-realm wrapper was invoked,
  not that an email was received, the notification appeared, or its message
  identity was authenticated. The Proton page is itself untrusted as a source
  of security assertions.
- `attempts=0` does NOT prove Proton creates no notifications. The pilot
  misses notifications that happened before the first click, calls through
  a cached constructor, other tabs/windows, and service-worker
  `registration.showNotification()`. A notification still appearing in
  Post-Apollo with zero page attempts would be useful architectural evidence
  of an alternate path, not a test failure.
- This uses MAIN-world interception and should be treated as a security and
  compatibility experiment. Firefox-family MAIN-world support must be
  tested on the actual browser before claiming live compatibility.
- **No message ID is available** and no existing Post-Apollo notification
  becomes an actionable mail binding. All six provider MAIL buttons remain
  disabled. The relay, private ledger and independent correlation policy
  remain unactivated by this change.

## Mark Read UI readiness inspection (read-only pilot, 2026-10-22)

To begin the operator's first real-action goal without guessing message IDs, the
Chromium + Firefox companion now has a **click-initiated, `activeTab`-scoped**
page readiness probe, using the browser `scripting` permission:

1. On the user's explicit extension-button click in an exact Proton-origin tab,
   the companion runs `readiness_probe.js` in that specific tab. This
   read-only probe requires no native host installation and remains available
   even if the host is disconnected.
2. Independently, the extension tries the native read-only `PING/PONG`
   handshake; its success does NOT turn page observations into message IDs.
   The probe inspects only button ARIA labels / `title` attributes for the
   exact English `Mark as read` label. It returns only a capped count of
   0, 1 or 2 candidates plus `messageIdentityVerified:false` and
   `canMutate:false`. The background script checks the returned schema.
3. The readiness result is reported only to the extension's developer console; it is
   never sent to the native host or Notifications history. No message subjects,
   text, addresses, page URLs, tokens, session storage, mail IDs or DOM are
   exported. The probe never clicks a page control.

A single matched control **does not** prove the user is on a one-message view,
that the message belongs to a particular notification, or that the control
will mark that exact email. Non-English sites, inaccessible labels, invisible
elements, 0 or multiple matches can all fail closed or be ambiguous. No
control is considered actionable on the basis of this probe alone.

**Do not enable MAIL buttons on this evidence.** Further separately approved
live validation must establish a provider-authenticated account, immutable
message identity, event-to-message correlation, and an operation receipt.
Do not infer identity from a label, subject, hostname or internal URL.
The eventual first supported action will be Mark Read; no mailbox mutation
is part of this slice.

**Permissions delta:** the extension manifests now request `scripting`
in addition to `activeTab` and `nativeMessaging`. That is a capability
