## IMPLEMENTATION

C3d #1451 is merged, with independent post-merge audit [#6712858600](https://github.com/kudokudo1/The-Post-Apollo-Project/pull/1451#issuecomment-6712858600). It proves a real Fedora offline guest can install and verify a signed fake-status RPM, detect tampering, repair, execute a confined fake host, and erase package plus temporary signer key. Its self-generated CI signer ships its public key beside the RPM: this is deliberately **not genuine release provenance**.

C3e-A implements the first strictly offline, **non-production** policy boundary:

1. An **externally supplied, previously pinned root fingerprint** and its standalone public key are required. The program never reads the root fingerprint from the candidate artifact, repository package, adjacent manifest or builder's public key. A substituted root public key is rejected.
2. A **detached OpenPGP signature by that root** must authenticate the exact release policy bytes. The verifier uses a fresh temporary GPG keyring containing *only* the requested root key, and `gpgv` checks signature validity, signer fingerprint and separation from the user's default GPG keyrings. There is no automatic trust-on-first-use.
3. The root-signed policy identifies the protected release ID, a policy epoch, a minimum release sequence, specifically approved signer fingerprints with `active`/`revoked` states, and approved release sequence/size/SHA-256 triplets.
4. The candidate brings a detached OpenPGP signature on an exact release manifest, a candidate signing public key, and an artifact. The candidate signing key is cryptographically usable **but not trusted** unless the independently root-signed policy lists its fingerprint as active and authorizes this exact release digest, sequence and size.
5. The caller must also supply a **trusted external policy-epoch floor and release-sequence floor**. This simulates durable anti-rollback state; older yet correctly root-signed policies, release downgrades, unknown/revoked signers, modified manifests or artifacts, unexpected fields and duplicate keys fail closed.
6. CI generates three short-lived test-only identities (one simulated root, signer A and signer B) inside the runner's temporary directory. Real `gpgv` signatures are checked for successful root delegation, forged-root refusal, policy substitution, signer revocation and root-signed signer rotation. The private keys disappear with the CI job and are not committed, installed, distributed or promoted as release identities.

## HOW TO USE

No operator desktop steps. The new workflow runs real temporary GnuPG signatures on GitHub's ephemeral Ubuntu runner. It is not a release-signing tool and no real production root is configured. The CLI is strictly opt-in and requires explicit `--root-public`, `--root-fingerprint`, `--policy`, `--policy-signature`, `--delegated-public`, `--manifest`, `--manifest-signature`, `--artifact`, `--minimum-policy-epoch`, and `--minimum-release-sequence`. For the fixture test, those inputs are generated by the test harness, not provided by a human.

## WATCH OUT FOR

**C3e-A does not establish a real production release trust root.** An operator must separately designate an organizational authority, approve its public fingerprint through an out-of-band authenticated channel, decide whether to use offline/HSM-backed signing and recovery, define delegation/rotation/revocation ceremonies, protect key custody, and establish signed-policy distribution. The verified CI identities are synthetic and their keys are discarded.

The external monotonic floors are **arguments**, not tamper-resistant persisted state. Production requires an authenticated local monotonic store and restoration rules resistant to rollback. This pilot does not verify a real signed RPM package header, perform a Fedora `rpm-ostree` transaction, attest executable memory, authenticate client processes or approve any real API grant. Those are separate acceptance gates.

Even if this offline policy test passes, importing a root signing public key into the operator's RPM trust database, installing release packages, changing systemd, SELinux, or turning on any credential action still require explicit operator authorization and independent review.
