# SECURITY // POST-APOLLO

Security reports are welcome when they concern an actual security or privacy risk.

## What belongs here

Depending on the repository, security issues may include:

- exposed credentials, tokens, private keys, or sensitive data;
- command injection or unintended command execution;
- privilege escalation;
- unsafe file operations or destructive path handling;
- authentication, authorization, or session bypass;
- remote-control or cross-machine trust failures;
- input-routing failures that cross user or seat boundaries;
- unsafe automation or GitHub Actions behavior;
- dependency or supply-chain compromise;
- unintended disclosure of private repository or user information.

For documentation-, philosophy-, archive-, or artwork-heavy repositories, security scope is usually limited to automation, scripts, workflows, executable examples, embedded secrets, or accidental sensitive-data exposure.

## What is not a security report

Normal bugs, feature requests, stale documentation, architectural disagreements, philosophical disagreements, visual defects, and ordinary compatibility problems should use the normal issue process.

## Reporting

If GitHub offers a private **Report a vulnerability** option for this repository, use it.

If no private reporting channel is available, open a minimal issue asking the repository owner for a private security contact. Do **not** include exploit details, credentials, private data, or a working proof of concept in a public issue.

## Good-faith research

Please avoid:

- accessing data that is not yours;
- disrupting systems or other users;
- persistence beyond what is necessary to demonstrate the issue;
- destructive testing;
- public disclosure before the maintainer has had a reasonable opportunity to investigate.

There is currently no guaranteed response-time SLA and no standing bug-bounty promise.

The goal is coordinated repair, not theater.
