# Post-Apollo Notifications // Proton Mail dual-adapter contract

**State:** Development foundation. **No mailbox integration is live.**

This file documents only the Notifications implementation boundary; it is not a Hospital authority rule. Do not enable account access, mailbox mutation or browser extension installation merely by merging this code.

## Goal

One Notifications **MAIL** deck, two independently authenticated adapters:

- **Browser companion (Chromium + Firefox):** Free and paid Proton plans. Must inspect only an explicitly authorized Proton Mail tab. Proton native Snooze is possible only after the site interaction, message selection and result can be reliably verified. No private undocumented Proton HTTP API assumed.
- **Proton Mail Bridge:** Paid plan, IMAP loopback. Read, Archive, Trash, Spam and Star may be implemented with verified IMAP mailbox identity/flags. Native Snooze is NOT supplied by Bridge, even on paid plans.

The MAIL deck already exists. Native notification actions remain available when the sender advertises them, but these are unrelated to provider authentication. Until a real adapter provides a verified message reference, the six buttons **stay disabled**.

## Architecture

```text
Browser notification --> NotificationsService (history + notification id)
                               |
                  PRIVATE trusted message binding
                               |
                      Mail action policy
                               |
            +------------------+------------------+
            |                                     |
    Browser Companion                    Bridge IMAP (paid)
    Proton origin only                   loopback + verified TLS
    Snooze + supported web ops           five IMAP-supported ops
            |                                     |
            +------------------+------------------+
                               |
                 Provider-confirmed result receipt
                               |
                  MAIL UI final state update
```

## Invariants

1. **One message, one action, one adapter.** The planner prefers Bridge for its five supported actions and the browser for Snooze. It can choose the browser for another action only if that adapter independently has a verified identity for the exact message and advertises that capability. No silent retry on a second adapter after a partial/uncertain mutation.
2. **Never guess identity from subject, sender, notification text, timestamps, web hostname, HTML position, or an apparent Proton internal URL.** A binding must be generated by an authenticated, trusted adapter from a verified message. Browser and Bridge message references are not assumed equivalent.
3. A binding is private and expires; **do not persist opaque references or secrets in notification history**. No Proton account password, Bridge-generated password, cookies, browser storage tokens, message body or unencrypted mail content should be logged or put on the desktop notification bus.
4. **Trash and Spam require explicit confirmation.** Clicking an available MAIL action is not an authorization to touch another email.
5. Provider dispatch means **pending**, not success. Show completion only after a verified response matching the same action, account, event, message reference and request id; reconnect/failure/timeout must not infer success.
6. Bridge must bind **127.0.0.1**, a verified TLS mode/certificate, a single authenticated account, and **UIDVALIDITY + UID + mailbox**. An IMAP move can change UID, so the adapter must refresh binding/receipt before subsequent actions. Never bypass certificate verification or use a Proton account password instead of Bridge credentials.
7. The browser companion must pin the exact extension identity in the native-host allowlist: Chromium uses `allowed_origins` plus a `chrome-extension://` caller; Firefox uses `allowed_extensions` plus the explicit Gecko add-on ID. The native host independently checks the caller using browser-specific launch arguments. The native host manifest and extension installation are **separate explicit operator approvals**. No extension broad browsing permissions, page-injected scripts or session-token copying.
8. Preserve Notifications SITE/APP, DND, ZZ, FAVS, CLEAR ALL, native default click, Apollo widget routes and ⇲ Bring Here. **Mail Snooze is not Notification ZZ; Mail Star is not Notification Favorites.**

## Implemented in this slice

- `services/notifications/mail/ProtonMailActionPolicy.js`: pure deny-by-default action selection, account binding, destructive action confirmation gate, provider receipt verification.
- `ProtonBrowserCompanionPolicy.js`: exact Proton origin and capability attestation policy; no verified mailbox reference means no capabilities.
- `ProtonBridgeAdapterPolicy.js`: loopback/certificate prerequisites; five supported operation names, no Snooze and no socket writes.
- `integrations/proton/browser/`: **uninstalled**, read-only extension and native-host `PING/PONG` skeleton. User click on a Proton tab is required. It sends **no message identities, mail contents, credentials or mutation operations**. The host refuses all commands except a versioned PING and always reports `mailboxAccess:false`.
- Offline tests for message binding, adapter preference, expiry, cross-account refusal, receipt matching and read-only handshake.

## Remaining implementation gates

1. Browser: test each supported browser family's extension API and the real Proton UI to establish a **stable account and exact message identity** from the authenticated page without capturing session secrets. Explicit local installation + validation required. Do not automate uncertain DOM selectors.
2. Browser: implement each action behind confirmed UI-specific capability, including Snooze time choice (preset time works on Free). No unverified API calls.
3. Bridge: after paid access and explicit local installation approval, design a local-only TLS-verified IMAP client using **Bridge-generated credentials held only in the OS secret store**. Add a read-only mailbox identity probe, then controlled operations with refresh of UID after moves.
4. Correlate a browser notification to a confirmed mailbox event through a trusted adapter-controlled event binding. Old saved notifications without identity do not become writable.
5. Connect trusted bindings + provider receipts to NotificationsService and MAIL buttons, using a pending/confirmed/failed UI. Include rollback and no-duplicate-dispatch tests.
6. Only after dedicated test evidence, real Quickshell/browser/Bridge acceptance, and operator approval: enable actions on the local machine.


## Multi-browser companion foundation (2026-10-22)

The browser-facing pilot is shared, **not a Brave-only mailbox adapter**:

- **Chromium-family (Brave, Chrome/Chromium, Edge, Opera):** use `integrations/proton/browser/manifest.json` (Manifest V3 background service worker), `background.js`, and `native-host.example.json`. Browser-specific host registration and the actual exact Chromium extension ID are not installed or assumed; each browser must be tested separately.
- **Firefox:** stage `manifest.firefox.json` **as `manifest.json`** in an isolated extension package with the same `background.js`. Its Manifest V3 background uses `scripts`, with the explicitly pinned Gecko ID `postapollo-proton@extensions.invalid`. Stage `native-host.firefox.example.json` under the browser's proper native-messaging host location with its `allowed_extensions` and an approved absolute executable path. Firefox's native host launch convention uses a manifest-path argument followed by the add-on ID.
- **Mullvad Browser:** Firefox-derived, but opt-in feasibility-only until separately validated. It is not auto-installed, and reducing fingerprinting protections to make the extension work is not authorized.
- All families send exactly `{"protocol":1,"kind":"PING"}` after a user click on an exact `https://mail.proton.me`-origin tab. The host returns **read-only** `PONG` with `mailboxAccess:false`, `messageIdentityVerified:false` and no capabilities. No browser gets mailbox privileges from this compatibility slice.
- A manually approved host environment must pin `POST_APOLLO_PROTON_EXTENSION_ORIGIN` for Chromium or `POST_APOLLO_PROTON_FIREFOX_EXTENSION_ID` for Firefox. The host rejects wrong ID, mismatched family, unexpected manifest-path shape, unknown commands and broad/wildcard identities. A separate native-host manifest must be registered where the selected browser expects it.
- Browser family is a **transport distinction**, not an email provider. Chrome support does not mean Gmail support. Proton identity, action dispatch, private event binding and provider-confirmed receipts remain future work shared across all browser families.
- Offline simulated tests execute the shared background logic using both browser API styles and verify origin restrictions, read-only replies, host identity and permission boundaries. No end-to-end browser installation, real Proton account, message identification or MAIL action was tested or activated.

## Mark Read UI readiness inspection (read-only pilot, 2026-10-22)

To begin the operator's first real-action goal without guessing message IDs, the
Chromium + Firefox companion now has a **click-initiated, `activeTab`-scoped**
page readiness probe, using the browser `scripting` permission:

1. On the user's explicit extension-button click in an exact Proton-origin tab,
   the companion runs `readiness_probe.js` in that specific tab. This
   read-only probe requires no native host installation and remains available
   even if the host is disconnected.
2. Independently, the extension tries the native read-only `PING/PONG`
   handshake; its success does NOT turn page observations into message IDs.
   The probe inspects only button ARIA labels / `title` attributes for the
   exact English `Mark as read` label. It returns only a capped count of
   0, 1 or 2 candidates plus `messageIdentityVerified:false` and
   `canMutate:false`. The background script checks the returned schema.
3. The readiness result is reported only to the extension's developer console; it is
   never sent to the native host or Notifications history. No message subjects,
   text, addresses, page URLs, tokens, session storage, mail IDs or DOM are
   exported. The probe never clicks a page control.

A single matched control **does not** prove the user is on a one-message view,
that the message belongs to a particular notification, or that the control
will mark that exact email. Non-English sites, inaccessible labels, invisible
elements, 0 or multiple matches can all fail closed or be ambiguous. No
control is considered actionable on the basis of this probe alone.

**Do not enable MAIL buttons on this evidence.** Further separately approved
live validation must establish a provider-authenticated account, immutable
message identity, event-to-message correlation, and an operation receipt.
Do not infer identity from a label, subject, hostname or internal URL.
The eventual first supported action will be Mark Read; no mailbox mutation
is part of this slice.

**Permissions delta:** the extension manifests now request `scripting`
in addition to `activeTab` and `nativeMessaging`. That is a capability
expansion and must be independently reviewed before user-approved installation.
No always-on content scripts, broad host permissions, cookie access or
unprompted page inspection are added. Browser-family variations and Mullvad
privacy opt-in rules remain in force.

**Developer checks:** `python3 tests/notifications/test_proton_readiness_probe.py`
plus the existing multi-browser and Proton policy tests. These are simulated
DOM/browser tests only, not live Proton certification.

## Read-only diagnostic follow-up (2026-10-22)

After selecting an unread Proton message, the original first-pass probe still
logged `no unambiguous read-control candidate`. That string conflated **zero**
and **two or more** recognized controls. The source does not establish which
occurred; do not assume the page lacks a Mark Read action.

The opt-in, exact-origin, active-tab-only `PROTON_READINESS_V2` probe now
reports only bounded, non-content observations to the *extension's own console*:

- `exactEnabled`: exact English `Mark as read` aria/title matches available.
- `exactDisabled`: same exact match, but disabled.
- `otherEnglishReadLabels`: differing read/unread label forms, not identities.
- `unlabeledControls`: button-like controls missing both aria/title.
- `checkedControls`: generic checked checkbox/checkbox-role count, **not**
  proof of selected mail messages.
- `inspected`: number of button-like controls examined, at most 500.
- `truncated`: if there were over 500 and therefore the scan was incomplete.

No raw strings, HTML, page URLs, message bodies, subjects, account identities
or message IDs are passed back. No mailbox mutation or native host installation
is required. The output always says **identity NOT verified**.

To use: pull the updated repository, open `brave://extensions`, choose
**Reload** on the unpacked Proton Companion, open its service-worker console,
open Proton Mail, select exactly one unread message checkbox, click the
companion icon, and inspect the new `read-only UI counts` line. The
`native host not connected` warning is expected. Firefox-family installs
need an equivalent reload.

Results distinguish likely cases but do **not** grant permission to click or
map a notification to mail. If there are zero controls or ambiguous UI
semantics, live authorized research is still required; preserve fail-closed
operation and do not infer identity from a subject, timestamp, or URI.

## Source-verified read/unread toolbar identifiers (2026-10-22)

The operator's live Brave V2 diagnostics showed 359 controls (347 unlabeled),
then 362 controls (350 unlabeled), zero text-label read matches in both,
and checked-control count increasing from zero to one after a single
unread-message selection. This verifies only a generic checkbox change,
**not** a message ID.

Source inspection of Proton's public maintained WebClients repository confirms
`applications/mail/src/app/components/toolbar/actions/ReadUnreadButtons.tsx`
supplies `data-testid="toolbar:read"` and `data-testid="toolbar:unread"`
to its shared `ToolbarButton`. The shared component forwards attributes
to a native button and renders the human-readable `title` via a separate
Tooltip. Thus our earlier button `aria-label` / native `title` scan can
miss the correct control even when the button exists.

The V3 diagnostic **only compares those two literal test IDs** and returns
separate bounded counts for enabled and disabled read/unread toolbar buttons.
It continues to report the previous non-sensitive counts; no arbitrary
`data-testid`, DOM, text or IDs are exposed to the native host, logs,
desktop notifications, or history. No clicking, no mutation, no confirmed
message identity, and no assumption that every deployed Proton release uses
the same source version. An absent toolbar button may reflect read state,
selection state, UI version, or that element not being in the scanned document.
