## IMPLEMENTATION

- Camera already has a user-initiated `previewSelectedTrash()` which sends `preview-selected` to the Camera backend and returns a single selected-file preview with `planId` plus the selected `path`. `confirmSelectedTrash()` already consumes that short-lived plan through `trash-selected PLAN_ID MOVE_TO_TRASH`, moving the validated file to **recoverable GIO Trash**. The CLI independently validates source file, ownership, allowed gallery scope, one-use plan and age. This U5 change **does not** replace any of those checks, operations, or their backend.
- The U1 shared `TrashLifecycleActionDeck` accepts a separate, opted-in `resourceRevisionKind: "camera-plan"` for an exact 32-character lowercase hexadecimal preview plan ID. The existing default SHA-256 and U3 decimal `store-counter` remain unchanged. This plan ID is only a request identity; neither the generic deck nor its UI flags authenticate, grant or execute deletion.
- Camera's Gallery final `CONFIRM TRASH` bespoke ActionButton becomes the shared TRASH button. It appears **only after** an explicit preview, is scoped to one Camera Gallery selection, and never displays RESTORE or BURN.
- Camera's new `reviewSelectedCameraTrash(ownerId, resourceId, expectedRevision)` requires the Camera window to be open in Gallery, no busy/region/Zoom transition, exact fixed owner `camera-gio` and opaque resource label `camera-gallery-selection`, an exact backend-previewed 32-hex plan ID, and current selected path consistency across `selectedPath`, `selectedRecord`, `selectedTrashPreview` and the loaded Gallery file list. On success it invokes unchanged `confirmSelectedTrash()` once. The shared event never includes an arbitrary file path.
- A stale/changed selection, unavailable plan, forged caller owner, wrong view, pending action, or missing Gallery membership refuses before calling the backend.
- Camera's separate Trash++-hosted Cleanup queue (Batch/Grid/Swipe/Hunt) and Desktop screenshot cleanup retain their existing queue, validation and one-click/plan semantics. Their UI is **not** migrated in U5. `CameraCleanupView.qml`, its queue, and all Burn paths remain untouched.
- Protected Hospital, Weather originals, Finance, Notes/To-do, company, social, Identity and Time Machine records are **not included** in U5's operation.

## HOW TO USE

After independently authorized merge and workstation sync: open **Camera → GALLERY**, select an image or supported media file, click **MOVE SELECTED TO TRASH** to obtain the validated preview, then use the shared **TRASH** button in the confirmation row. **CANCEL** still discards the preview. The backend moves only that one unchanged, approved file into GIO Trash. Later restore it through the existing Trash++ file Restore operation (U4 UI adaptation is separately proposed in PR #1962).

## WATCH OUT FOR

1. **No new authorization:** A Camera plan ID is a short-lived bearer preview identifier already generated by Camera. An in-memory UI field is not a production permission boundary. The original backend retains source-path, signature, plan-age and one-use checks, and must not be bypassed.
2. **Not universal file deletion:** This is one selected-media Gallery file, not an arbitrary path chooser, recursive directory purge, batch queue rewrite, new generic Trash API or a legal-record deletion permission.
3. **Gallery freshness:** If a Gallery rescan or selection change removes an item, U5 refuses. The user can reselect and obtain a fresh preview through the existing control.
4. **No Burn:** The deck sets `showBurn: false`; Camera does not gain permanent deletion. GIO Trash retention and Restore remain OS/back-end owned.
5. **No protected source modifications:** This does not authorize Hospital, Finance, Weather, company or social data deletion, and does not change U2 deny-only source review or V3 protected Archive.
6. **Concurrent work:** U4 remains an unmerged draft PR #1962, restricted to `modules/Trash.qml` and `scripts/trash/trash_cli.py` plus tests; U5 deliberately avoids those files.
7. **Operator authority:** Starting U5 permits bounded GitHub development, not automatic local machine edits, PR merge, live activation or final acceptance.
