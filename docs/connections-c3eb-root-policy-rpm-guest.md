## IMPLEMENTATION

C3e-A PR #1461 is merged. Its offline policy verifier denies a candidate's self-supplied signing key unless a separately pinned root authorizes the signer and the exact artifact digest. C3d PR #1451 previously installed a fake read-only status service signed by a disposable RPM signing key but imported that disposable public key without a separate release policy.

C3e-B is a **test-only release admission / installation bridge**, reusing both code paths:

1. Under an opt-in flag, the C3d Fedora builder signs a detached release manifest with the *same ephemeral signing identity* used for native RPM signing. The legacy C3d four-file output remains the default; C3e-B produces six public-only artifacts.
2. A separate CI-runner GnuPG home creates a **different ephemeral root**. That root independently signs a strict C3e-A policy authorizing the delegated signer fingerprint and **exact SHA-256/byte size/sequence** of the real built fake RPM. Root identity and private key never enter the candidate directory or Fedora guest.
3. The existing C3e-A `C3eReleaseAdmission.py` must approve the actual signed fake RPM. The pipeline also rejects substituted root fingerprint, tampered RPM, already-revoked signer (with a properly root-signed *revoked* policy), and release downgrade through the independently supplied sequence floor.
4. Only after all negative and positive policy tests pass, a **separate approved staging directory** receives a byte-for-byte snapshot of the signed RPM plus the C3d disposable public verification artifacts. The runner rechecks the admitted SHA-256 digest and passes that digest as its own CI input to the guest.
5. The C2r Fedora guest driver, only when explicitly given `C3EB_APPROVED_SHA256`, stages a root-approved digest separately from the RPM and requires the exact `C3EB_PASS` serial marker. Its C3d preinstall gate checks that SHA-256 **before importing any RPM signer key or installing the package**, then verifies the native package signature, installed rpmdb ownership/integrity, tamper refusal/repair, C3b/C3c systemd/D-Bus/SELinux identity, and signed RPM/key cleanup.
6. The existing C2r, C2s and C3d workflows run without this opt-in digest and preserve their older test scopes. No C2z Silverblue, CPU++ QML, production broker or real provider is modified.

## HOW TO USE

No operator desktop actions. Only the GitHub workflow `.github/workflows/connections-c3eb-approved-signed-rpm.yml` generates the CI-only root and runs the offline Fedora guest. Root public/private keys and root policy stay on the disposable runner; only a *validated digest* of approved bytes goes to the guest. Real production roots, credentials, system packages and user machines are untouched.

## WATCH OUT FOR

**This is not production release provenance.** The standalone root is generated by the same GitHub CI job *after* observing the candidate. The root is kept physically separate from the package builder, and the new trust step authenticates the test RPM's bytes against that simulated root, but no organization has independently enrolled that root as a trusted authority. A malicious/compromised CI pipeline could create a new root and authorize a forged package. Real release engineering needs pre-enrolled operator-approved fingerprints, protected offline/HSM signing keys, independent reproducible release manifests, durable and rollback-resistant policy state, verified distribution, root rotation and recovery.

The staged guest hash is checked before installation, but this scripted test does not implement a full production verification-to-execution file-descriptor binding or cryptographic measurement of Python code in memory. The guest separately verifies a C3d self-signed native RPM signature; the separate root authorizes the **RPM artifact digest** and **delegated detached manifest signer**, not a production RPM keyring enrollment. Source/policy package ownership remains fake-only. Success does **not** authorize native Silverblue installation, any production service, user/app authentication, provider API, NAS, Social/TASKS content, or credential grants.
